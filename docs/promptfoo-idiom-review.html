01Short answer

Your instinct is half right.

Verdict

The solver side is already idiomatic — you’re doing essentially what promptfoo’s “Evaluate Coding Agents” guide prescribes. The one place the round peg is jammed into the square hole is grade_rubric.py: it runs an entire second coding agent (the verifier) as a subprocess inside a Python assertion.

That’s where the old agentic-dx-improvement harness shape (verify_task.sh) is still bleeding through. promptfoo’s mental model is “providers do agentic work; assertions are cheap checks on what a provider returned.” You’ve inverted that for the verifier — it’s an agent modeled as an assertion.

02What’s already “the promptfoo way”

These match the guide almost exactly, so the round-peg worry doesn’t apply. Don’t touch them.

Keep as-is
  • Solvers as native agentic providers (anthropic:claude-code, openai:codex) — the guide’s Tier-1 SDK pattern verbatim. You correctly killed solve.sh.
  • Multi-agent A/B via multiple providers + one shared test suite — exactly the guide’s “compare agents” pattern.
  • Per-provider working_dir, MCP servers, and plugins/skills declared in provider config.
  • seed.js as a beforeAll extension — extensions are the sanctioned setup/teardown hook.
  • weight + threshold on assertions.
  • run.sh credential injection, Maven warm, --no-cache — legitimate environmental glue (the guide itself says use --no-cache during dev), not an anti-pattern.

03The real problem: the verifier is a provider wearing an assertion costume

grade_rubric.py reimplements ~400 lines of what promptfoo’s provider runner already gives you for free — timeout, retries, port freeing, isolated home, stream-json log capture — because promptfoo can’t see into a subprocess you spawn from an assertion.

The most damning symptom is in your own docstring:

“the agentic verifier this grader spawns runs as a subprocess, invisible to promptfoo, so its tool calls are not counted here (nor is its cost).”
Why this matters

For a DX benchmark whose entire point is measuring cost / tokens / effort, half the run’s cost being off the books is a substantive measurement gap, not just a style nit. That alone justifies the reframe.

Secondary symptoms, all consequences of the same inversion:

  • No caching, retry, parallelism, or tracing from promptfoo — you hand-rolled all of it.
  • A whole class of silent-zero failures (“did the verifier write verify-result.json?”) you’ve already had to harden against twice.
  • The verdict is a disk round-trip (write JSON file → read JSON file) instead of a return value.

04The reframe: verifier = provider, in a second phase

The verifier is an agent that produces a judgment. So make it a provider. Concretely, a two-phase run (orchestrated by run.sh, same as today):

Phase 1 — promptfooconfig.yaml

Solvers solve, exactly as now. Output: the seeded workspaces on disk.

Phase 2 — verify.yaml

The verifier is the provider — one per solved workspace. Assertions become trivial checks on its structured verdict.

# verify.yaml — phase 2: the verifier graded as a first-class provider
providers:
  - id: anthropic:claude-agent-sdk
    label: verify-codex
    config:
      working_dir: workspaces/codex        # the solved app
      mcp: { servers: [ playwright ] }
      output_format: <rubric JSON schema>   # structured verdict, no disk round-trip
  - id: anthropic:claude-agent-sdk
    label: verify-claude
    config: { working_dir: workspaces/claude, ... }

prompts: [ file://verify_prompt.md ]

tests:
  - assert:
      - type: is-json              # verdict shape
      - type: javascript           # tiny: pull score, check the floor
        value: "return output.total / output.max >= 0.6"
      - type: cost                 # NOW promptfoo tracks verifier cost
        threshold: 0.5
      - type: latency
        threshold: 600000

What this buys you

Wins
  • Verifier cost / tokens / turns / trace become first-class promptfoo columns — the gap closes.
  • output_format (JSON-schema structured output, which claude-agent-sdk supports) means the verdict comes back parsed in the response — no more verify-result.json on disk, no more “did it write the file?” silent-zero.
  • promptfoo owns retries / timeout / caching — delete most of grade_rubric.py (it shrinks to a ~20-line score check).
  • No cross-config chaining needed (promptfoo has none natively): the workspace dir on disk is the handoff — which you already do, just made explicit across two clean provider→assert phases instead of smushed into one assertion.
Don’t do this instead

Avoid trying to do it with llm-rubric + a custom grading provider: llm-rubric feeds the grader plain text via the Messages API and can’t start a server or drive Playwright, and its grading provider’s working_dir can’t vary per row. “Verifier as its own provider, one per workspace” sidesteps all of that.

05Smaller idiom wins you’re leaving on the table

1 · Hand-rolled trace namedScores → native assertions

Your _trace_metrics (skill/tool/turn counts, archaeology, denials) partly reinvents what promptfoo now exposes natively: cost / latency assertions and trajectory assertions (trajectory:step-count with a command pattern). “Did it run mvn?”, “did it hit the Vaadin MCP?”, “did it spelunk jars?” are exactly what trajectory asserts are for — assert the path, not just the answer.

Keep

Your one genuinely-justified custom bit is the cache-token column — promptfoo’s top-level token columns drop cache_read, which dominates agentic runs. Keep that; drop the rest.

2 · No Tier-0 baseline

The guide explicitly recommends a plain-LLM row to prove the agent/skills actually add value. You have none — so you currently can’t show that the Vaadin skills move the needle, which is presumably the thesis of the whole benchmark.

3 · --repeat 3

Agentic runs are non-deterministic; a single sample per agent is noisy. The guide flags this.

06What to keep custom (it’s not all a smell)

  • grade_static.py is fine as a Python assertion — custom Python asserts are a first-class feature, and it reads workspace files (not output), which native contains can’t. Lightweight, legitimate cheap gate. Not the round peg.
  • seed.js and run.sh — keep.

08Recommendation

Bottom line

The current setup is well-engineered and works — this isn’t “you did it wrong,” it’s “one component is modeled inside-out.”

If you only do one thing: promote the verifier from an assertion to a provider in a second phase, with output_format structured output. It closes the cost-visibility gap (the substantive win), deletes the most fragile ~300 lines you maintain, and removes a whole class of silent-zero failures. The trace-assertion and baseline points are nice-to-haves on top.

Next step, if you want it: a draft verify.yaml + the trimmed grade_rubric.py (now a ~20-line score check) + run.sh wired to run both phases — diffable against what you have today.
