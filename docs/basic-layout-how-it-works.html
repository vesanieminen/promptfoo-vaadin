How the basic_layout benchmark works

Three coding agents each solve the same Vaadin layout task; a fourth agent grades each result against a rubric. It runs as two promptfoo evals chained by one wrapper script — a solve phase and a verify phase.

★The one idea that shapes everything

promptfoo has a strict division of labour. Internalise this and the whole layout falls out of it.

Providers do the work

A provider is something promptfoo runs and measures — an LLM, or here a full coding agent that writes files, runs Maven, and drives a browser. promptfoo natively tracks its cost, tokens, latency, retries.

solver solver verifier

Assertions just check the output

An assertion is a cheap, deterministic check on what a provider returned. Here they're two small Python files that read a score and turn it into pass/fail + diagnostic columns. They do not spawn agents.

grade_static.py grade_verdict.py
Because the verifier is itself an agent, it is a provider, not an assertion.
That single decision is why solving and verifying are separate rows — and why the verifier's cost is now visible. The whole design below is this rule, applied twice. (see docs/ADR-verifier-as-provider.md)

2The three solvers (and why a baseline)

All three get the same task and the same Playwright browser. They differ only in who's solving and what Vaadin guidance they carry.

codex

The OpenAI agent

openai:codex:gpt-5.5, full file/command access. Codex has no plugin loader, so seed.js symlinks the Vaadin skills into its native .agents/skills/ location — apples-to-apples with the Claude row.

claude

The skills-equipped agent

anthropic:claude-code on Opus 4.8, loading the Vaadin agent-skills plugin (layouts, responsive-layouts…) plus the Vaadin docs MCP. This is the "with help" condition.

claude-no-skills

The control

Byte-for-byte the same as claude, minus the skills and the docs MCP. The gap between this row and claude is the benchmark's thesis: how much do the skills actually move the rubric?

Each runs isolated, so all three can run together (--max-concurrency 3).
Own working dir, own baked server port (8081/8082/8083), and an --isolated in-memory Playwright profile — so no port clashes and no shared browser-lock deadlocks.

3Phase 1 · Solve — promptfooconfig.yaml

Build the workspaces, let the agents solve, then gate on source.

seed.js — the beforeAll hook

Before anything runs, for each of the three solvers it (re)creates a fresh workspace:

  • copy task.md + reference PNGs in, copy the Vaadin skeleton into app/
  • strip rubric.md — the solver must never see how it'll be graded
  • bake the per-provider server.port into application.properties
  • write prompt.txt (the task, as the verifier will later read it)
  • for codex only: symlink the Vaadin skills into .agents/skills/

grade_static.py — the source gate + trace

A Python assertion on the solve row. It locates the workspace from the provider (not from output text — agentic providers return a chat message, not a path), reads the Java, and runs cheap deterministic checks:

  • @Route("basic_layout") present (critical)
  • uses HorizontalLayout / VerticalLayout (critical)
  • content area uses a Scroller
  • no inline styles in Java or templates · no leaked React/TSX views

Pass = all critical checks pass. It also attaches the solver trace as diagnostic columns.

Why the trace lives on the Phase-1 rows
The trajectory metrics — skill_calls, mcp_calls, api_archaeology_calls, num_turns, solve_seconds, cache_read_ktokens, output_tokens — describe the solver. They're read from the solver row's own provider metadata, so they belong here, not on the verify rows (whose metadata describes the verifier). Per ADR 0002 these are the real DX signal, but they are diagnostic only — they never gate pass/fail.

4Phase 2 · Verify — verify.yaml

A grader agent per workspace — run the app, look at it, score the rubric.

seed_verify.js — prep before grading

A second beforeAll, this time for the verify eval. For each workspace it:

  • restores rubric.md — the file phase 1 hid from the solver is now needed by the grader
  • deletes any stale verify-result.json from a prior run
  • frees the baked port, in case the solver left a dev server running on it

This is exactly why the restore can't live in seed.js: it has to happen after the solve and before the verify.

The verifier providers

Three anthropic:claude-agent-sdk agents (Opus 4.8, Playwright MCP), one per workspace. Each reads its prompt + rubric, runs app/run.sh, drives the browser across viewports, and returns its verdict as structured output:

// output_format JSON schema
{ "criteria": [
  { "section": "string",
    "score": 0, "max-score": 0,
    "bullets": [ {"name","score","feedback"} ] }
]}

"Which workspace am I grading?" is answered by which provider row it is — no dynamic config needed.

grade_verdict.py — score the verdict (~30 lines)

Because the heavy lifting is now the provider's job, this assertion is tiny. It:

  1. maps the row to its workspace (verify-codex → workspaces/codex)
  2. reads the verdict — structured output first, falling back to verify-result.json on disk
  3. sums section scores → normalizes to a 0–1 fraction (handles 21- vs 24-point totals automatically)
  4. passes if ≥ floor (RUBRIC_PASS_THRESHOLD, default 0.6) and emits per-section rubric_* columns

Within one run → all providers are together
The three solvers share one run as three columns. So do the three verifiers. There is no "three separate rows for the three agents" — it's one row, three provider columns.
Across the two runs → solve ≠ verify
Solve and verify are two separate evals (two run entries). The only thing tying a solve to its grade is the label: codex ↔ verify-codex. And REPEAT=n produces 2 × n runs.

6Why the verifier is a provider, not an assertion

This is the change this branch (reframe-verifier-as-provider, PR #15) exists to make. The earlier port did the opposite, and it hurt.

Old — verifier inside an assertion (grade_rubric.py)Now — verifier is a provider (verify.yaml)
Verifier cost / tokens / latency Invisible — a subprocess promptfoo can't see. ~half of every run was off the books. Native promptfoo columns (the verify-* rows).
Retries / timeout / concurrency ~400 lines re-implementing the provider runner by hand. promptfoo owns it. grade_verdict.py shrank to ~30 lines.
The verdict Disk round-trip + a class of silent-zero failures ("did it write the JSON?"). A structured-output return value (JSON file kept only as a fallback).
Isolated CLAUDE_CONFIG_DIR A per-workspace .claude-home the subprocess needed. Gone — the provider authenticates normally, so the token is now optional.

Why not just llm-rubric (the obvious "one row" answer)?

llm-rubric feeds the grader plain text. It can't start a Spring Boot server or drive Playwright — but this rubric is about how the rendered app looks and behaves across viewports. A text grader can't see that.

A single grading provider has a static working_dir. It couldn't point at a different workspace per row. "One verifier provider per workspace" sidesteps both problems — verification here is provider-shaped work.

So "combine solve + verify into one row" would mean re-burying the verifier's cost.
The two-run shape isn't overhead to clean up — it's the thing that makes the verifier's cost a first-class, measurable part of a benchmark whose entire point is measuring DX cost.

7Authentication — what run.sh does

Both phases are Claude/Codex agents, so both need auth. run.sh resolves one credential and injects it into the bench process only — never your shell or rc files.

Two modes — you pick by which credential you supply

sk-ant-api…
→ ANTHROPIC_API_KEY · bills the API key (solver + verifier)
sk-ant-oat…
→ CLAUDE_CODE_OAUTH_TOKEN · bills your subscription

The chosen var is set and the other unset, so exactly one credential is live — no precedence surprises.

It's optional now

Source order (first hit wins): $ANTHROPIC_API_KEY → $CLAUDE_CODE_OAUTH_TOKEN → basic_layout/.bench-token.

If none is found it warns and continues, falling back to your existing Claude Code / Codex login (Keychain). Supply a credential only to override that — API-key billing, or a login-less CI box.

Why this used to be required
The old subprocess verifier ran with an isolated config dir that couldn't read the Keychain. As a provider, it can — so the token went from mandatory to optional.

8Running it

# solve, then verify — one full pipeline pass
bash basic_layout/run.sh

# run the whole pipeline 3× for variance (each row is a ~30-min agentic pass)
REPEAT=3 bash basic_layout/run.sh

# one agent only (anchor the regex — the verify ids all contain "claude")
bash basic_layout/run.sh --filter-providers 'claude$'

# see the two runs side by side
npx promptfoo@latest view
Two flags that matter
--no-cache is required — agentic providers cache by prompt, so without it a re-run replays instead of re-solving. --max-concurrency 3 runs all three rows in parallel (safe: isolated workspaces, ports, and browsers).
