MCP vs CLI vs vanilla, again — same three rows at concurrency 2

A repeat of run 1's three Claude rows (skills + Vaadin MCP + Playwright MCP, skills + Vaadin MCP + Playwright CLI, vanilla), this time at max-concurrency 2 instead of 3. Two findings: the skills edge held and grew (claude beats vanilla on all three problems, +5 pooled points), but the run-1 transport tie did not perfectly reproduce — claude edged pw-cli by 3 points (within n=1 noise). And operationally: halving the concurrency made the agent-SDK teardown hang far worse — four rows had to be killed by hand.

  • Skills beat vanilla on every problem. claude (skills) topped vanilla 21–20 on basic_layout, 29–27 on basic_form, and 47–45 on md_ui_spec — +5 pooled points (94.2% vs 89.3%). As ever the gap is Vaadin idiom + correctness, not whether the app works.
  • Transport was not a perfect tie this time. Run 1 had claude and pw-cli dead-level on all three (20/30/48 each). Here claude edged pw-cli 97–94: tied on md_ui_spec (47–47), but +1 on basic_layout and +2 on basic_form (pw-cli matched vanilla's 27 there, not claude's 29). A 3-point swing across single runs is exactly the n = 1 noise the bench warns about — the transport remains rubric-neutral within that band.
  • Concurrency 2 was markedly more hang-prone. The agent-SDK teardown hang (agent finishes, subprocess never exits, barrier blocks) hit four rows that I killed by hand — basic_layout solve/claude, basic_layout verify/pw-cli, md_ui_spec solve/pw-cli, md_ui_spec verify/vanilla — plus all three basic_form solve rows carried the non-clean-exit flag. The morning's concurrency-3 sweep had just one. See §4.
  • The 480px breakpoint bug recurs — all three. Every row gates stacking at max-width: 379.98px, so at the rubric's 480px test the toolbar stays in row mode. A persistent benchmark signal, independent of tooling or concurrency.
  • Costs are distorted — don't compare them this run. Two solve rows were killed mid-hang and recorded $0 (claude basic_layout, pw-cli md_ui_spec), so the row totals ($20.00 / $14.02 / $9.99) understate the true spend unevenly.

4 The teardown hangs — concurrency 2 made it worse

The known agent-SDK exit hang: an agent finishes its work (workspace built / verdict written) but its claude-agent-sdk subprocess never exits, so promptfoo — which awaits process exit — blocks the whole --max-concurrency barrier. Each was confirmed by lsof/sample (parked on the binary's main-thread exit path, no live work) and unstuck with kill -TERM.

9 Caveats & data gaps

  • Four killed rows + recovered verdicts. See §4. Two verify verdicts (pw-cli basic_layout 20/24, vanilla md_ui_spec 45/48) came from on-disk verify-result.json after their verifiers were SIGTERM'd; promptfoo's own view shows those two cells as errored. Two solve rows (claude basic_layout, pw-cli md_ui_spec) recorded $0 and built fine.
  • Concurrency 2 ≠ run 1's concurrency 3. This run isn't a clean rubric re-test of run 1 — the concurrency changed (and with it the hang rate). The rubric numbers are still comparable (per-row work is independent), but the operational profile is the headline difference.
  • n = 1 per cell — treat ±1–2 rubric points as noise. The transport gap flipping from a 0-point tie (run 1) to claude +3 (here) is that noise in action.
  • Self-grading. Verifier and all three solvers are Claude — no cross-model anchor. Grading is mostly Playwright-measurement-based, which limits bias.
  • Cost is unreliable this run — two $0 solve rows. Use the morning's run 1 for any cost comparison. Verify cost is intact.
  • Token columns understate throughput by design — use cost (when present) for efficiency, not the built-in token counts.
